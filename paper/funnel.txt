Funnel de datos para el paper
=============================

Estado: borrador documentado desde el bucket de DigitalOcean Spaces, este repo
(`public-procurements-outcome-predictor`) y el repo previo
(`public-procurements-offerers-tagging`).

Importante: este archivo distingue entre (a) artefactos observados en el bucket,
(b) inferencias razonables a partir del codigo, y (c) puntos que conviene aclarar
manualmente antes de convertir esto en texto final del paper.

Decision de priorizacion:
- Para reducir lo mas posible el desbalance de clases, la descarga y el
  procesamiento de documentos priorizaron las licitaciones no exitosas
  (`unsuccessful` y `cancelled`) antes que las `complete`.
- Esto coincide con el orden del merge/cola de descarga en el codigo:
  `ids_unsuccessful.json` -> `ids_cancelled.json` -> `procurements.json`.
- Por eso las tasas de procesamiento son mucho mas altas para las clases no
  exitosas que para `complete`.


Funnel operativo: intentos, OK y no OK
--------------------------------------

Criterio usado:
- "OK" significa que existe el artefacto esperado o el flag correspondiente en
  `procurements_dataset.json` esta en `True`.
- "No OK con motivo" significa que el dataset conserva un `*_skip_reason` o
  `*_error`.
- "Sin evidencia de intento / no procesado" significa que no hay artefacto final
  ni motivo de fallo conservado en el JSON. Para la descarga de PBC PDFs, esto se
  atribuye a falta de tiempo por rate limiting de la DNCP al consultar tenders y
  descargar documentos. En etapas posteriores, si no hay motivo conservado, se
  mantiene como falta de tiempo o recursos computacionales salvo evidencia
  posterior.

Tabla principal:

| Paso | Universo elegible | Intentados con evidencia | OK | No OK con motivo | Sin evidencia de intento / no procesado |
| ---- | ----------------- | ------------------------ | -- | ---------------- | --------------------------------------- |
| Materializar `complete` desde `tagging/ids/ids.json` | 10,000 IDs | 10,000 | 10,000 | 0 | 0 |
| Descargar IDs `unsuccessful` desde DNCP | todas las paginas disponibles (3/3) | 3 paginas | 257 IDs | 0 | 0 |
| Descargar IDs `cancelled` desde DNCP | todas las paginas disponibles (4/4) | 4 paginas | 371 IDs | 0 | 0 |
| Merge de IDs por `tenderId` | 10,628 filas | 10,628 | 10,628 | 0 | 0 |
| Descargar PBC PDF | 10,628 procesos | 1,887 con evidencia (1,845 OK + 42 no OK con motivo) | 1,845 | 42 | 8,741 |
| Extraer texto desde PBC PDF | 1,845 PDFs PBC | 1,845 | 1,842 | 3 | 0 |
| Generar embeddings desde texto | 1,842 textos | 1,842 | 1,162 | 680 | 0 |
| Dataset supervisado final | 1,162 embeddings con `y` | 1,162 | 1,162 | 0 | 0 |

Detalle por status en etapas principales:

| Status | Dataset inicial | PBC PDF OK | Texto OK | Embedding OK |
| ------ | --------------- | ---------- | -------- | ------------ |
| `complete` | 10,000 | 1,273 | 1,270 | 844 |
| `unsuccessful` | 257 | 246 | 246 | 204 |
| `cancelled` | 371 | 326 | 326 | 114 |
| Total | 10,628 | 1,845 | 1,842 | 1,162 |

Detalle de no OK conservado:
- Descarga PBC PDF:
  - 42 procesos sin PDF tienen algun `pbc_skip_reason` conservado.
  - 12 tienen razon compacta `no_pdf_pliego`.
  - Los demas motivos conservados son mensajes del tipo "No se encontro documento
    PBC o carta de invitacion en ZIP..." con lista de archivos disponibles.
  - Estos 42 casos tambien pueden incluir fallas HTTP/red u otros errores de
    descarga registrados en `pbc_skip_reason` / `pbc_error`, segun el mensaje
    particular de cada fila.
  - 8,741 procesos sin PDF no conservan motivo en el JSON final; para esta
    documentacion se tratan como no procesados por falta de tiempo debido al rate
    limiting de la DNCP al consultar tenders y descargar PBCs.
- Extraccion texto:
  - 3 PDFs PBC no tienen `.txt` correspondiente.
  - Estos 3 fallos se deben a documentos escaneados: el extractor de texto no
    soporta OCR.
- Embeddings:
  - 671 fallos `embed:OutOfMemoryError`.
  - 9 fallos `embed:ValueError`.
  - OOM significa "out of memory": la GPU/CUDA no tuvo memoria suficiente para
    ejecutar el modelo sobre el micro-batch de chunks. El codigo reintenta
    reduciendo `chunk_batch_size` por mitades hasta llegar a 1; si aun con
    `chunk_batch_size=1` no entra en memoria, la fila queda marcada como
    `embed:OutOfMemoryError`.
  - La generacion de embeddings se corrio una sola vez sobre el conjunto
    disponible. Los documentos que fallaron no se reprocesaron con mas memoria ni
    con infraestructura alternativa por limites de costo/infraestructura.

6. Texto -> embeddings por chunks

Artefactos:
- `outcome-predictor/pbcs/embeddings/`: 1,162 `.pt`.
- 680 textos no tienen embedding `.pt`.

Conteo final por status entre embeddings:
- `complete`: 844.
- `unsuccessful`: 204.
- `cancelled`: 114.
- Clase positiva final (`y=1`, complete): 844.
- Clase negativa final (`y=0`, unsuccessful/cancelled): 318.
- Total supervisado usado en el paper: 1,162.

Codigo:
- `scripts/etl/embed_pbcs.py`.
- `src/models/embedder.py`.
- `src/data/procurement_target.py`.

Parametros relevantes:
- Encoder: `openai/gpt-oss-20b`.
- Chunk max length: 4096 tokens.
- Stride: 2048 tokens.
- Se guarda un `.pt` por proceso, con embeddings de chunks y target `y`.

Motivos observados de no embedding entre textos extraidos:
- `embed:OutOfMemoryError`: 671.
- `embed:ValueError`: 9.

Inferencia:
- La mayor reduccion despues de la extraccion ocurre por fallos de embedding,
  principalmente OOM en documentos largos o costosos de procesar. Aunque el
  pipeline procesa chunks en micro-batches CPU->GPU y desactiva la KV cache del
  modelo para ahorrar memoria, cada chunk puede tener hasta 4096 tokens y el
  encoder congelado es grande; algunos documentos siguen excediendo la memoria
  disponible.
- El subset experimental del paper corresponde a los 1,162 procesos con PBC
  descargado, texto extraido, embedding generado y etiqueta binaria usable.

[Aclarar]
- Si hubo corridas con `--max-doc-tokens`, `--shard`, multiples GPUs o cambios de
  `chunk-batch-size`.
- Los 680 textos sin embedding se consideran exclusion tecnica por limites de
  memoria GPU/costo de infraestructura despues de una unica pasada de embedding.

Version corta posible para el paper
-----------------------------------

The initial procurement pool contained 10,628 processes: 10,000 completed
processes materialized from a previous DNCP scraping pipeline and 628 additional
non-successful processes collected by status from the DNCP API. The PBC retrieval
stage obtained 1,845 PDF bidding documents, of which 1,842 were successfully
converted to text. Embedding generation with the frozen LLM succeeded for 1,162
documents, yielding the supervised subset used in the experiments: 844 completed
and 318 non-successful procurements. The main loss between text extraction and
the final experimental subset was due to embedding failures, mostly GPU
out-of-memory errors on long documents.


Notas para no sobreafirmar
--------------------------

- No decir que el subset final es representativo del universo DNCP.
- No decir que los 1,845 PBC son todos los PBC disponibles en DNCP; son los PBC
  efectivamente encontrados/descargados por este pipeline.
- No mezclar `tagging/pdfs` (ADA/CCO del proyecto anterior) con
  `outcome-predictor/pbcs/pdf` (PBC del paper actual).
- No usar `tagging/results` como label del paper actual: esos resultados son de
  `offererCount`, una tarea anterior distinta.
- Documentar los 680 textos sin embedding como exclusion tecnica observada, no
  como criterio conceptual del diseno experimental.
